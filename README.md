# Design-Partner Funnel

Пайплайн готовит аутрич дизайн-партнёрам HAIA по базе аккаунтов в Notion: находит у каждой компании свежий проверяемый повод, по правилу выбирает оффер, пишет 4 касания (email, LinkedIn, email, переадресация), прогоняет их через проверки кода и независимого рецензента и кладёт карточку в Notion на ревью.

**Пайплайн ничего не отправляет.** Отправка — вручную, после одобрения.

Все правила — в [`SPEC.md`](SPEC.md). Код их только исполняет: что брать, в каком порядке, какой оффер и прошёл ли текст проверки, решает код. Модель делает один вызов на аккаунт с фиксированным промптом и обязана вернуть JSON по схеме.

## Как это устроено

| Этап | Что делает | Кто решает |
|---|---|---|
| `select` | Берёт аккаунты и контакты из Notion по фильтрам `config.yaml`, раскладывает контакты по уровням (SPEC §2) | Код |
| `research` | Ищет поводы по обязательному маршруту источников (новости, сайт, вакансии, люди, база) | Модель (Claude Code с WebSearch / WebFetch) |
| — проверка поводов | Открывает каждую ссылку и ищет дословную цитату; проверяет свежесть (365 дней). Нет проверенного повода — письма нет | Код |
| — план | Тип повода → оффер: BUILDING→EMBED, CHANGE→BACKTEST, SCALE→REPLAY; допустимые основания дня 3 | Код (`pipeline/rules.py`) |
| `write` | Пишет 4 касания на каждого контакта | Модель, один вызов на аккаунт |
| — проверки | Длины, запрещённые фразы, HAIA в теле, числа без источника, правило дня 3, подписи… | Код (`check_package`) |
| `review` | Независимый рецензент без контекста автора; при FAIL — одна переписка | Модель, отдельный вызов |
| `publish` | Карточка аккаунта в Notion: поводы со ссылками, план, касания в READ + COPY | Код |

Статусы аккаунта: `selected → planned → written → ready → published`. Отдельно: `under_researched` (нет проверенного повода), `check_failed`, `review_failed`, `error`. Ошибка одного аккаунта не останавливает батч.

## Установка

1. Python 3.11+:
   ```bash
   pip install -r requirements.txt
   ```
2. **Claude Code CLI**, вход в аккаунт с подпиской (платный API не используется):
   ```bash
   npm install -g @anthropic-ai/claude-code
   claude            # один раз войти в аккаунт, затем выйти
   claude -p "ok"    # должен ответить без вопросов
   ```
   Пайплайн вызывает `claude -p --output-format json --model <алиас> [--allowedTools WebSearch,WebFetch]`. Проверено на Claude Code 2.1. Если флаги в вашей версии другие, поправьте `pipeline/llm.py::ClaudeCLI.build_cmd`.
3. Проверка без сети и без модели:
   ```bash
   python -m pytest -q
   python run.py eval
   ```

## Настройка

1. **Токен Notion.** Его выдаёт администратор корпоративного Notion: внутренняя интеграция с доступом к трём объектам — база аккаунтов, база контактов и страница, куда складываются карточки. Токен — только в переменной окружения, не в репозитории:
   ```bash
   export NOTION_TOKEN=secret_...
   ```
2. `cp config.example.yaml config.yaml` и заполните:
   - `accounts_data_source_id`, `contacts_data_source_id` — ID **data source** (не database). Как найти: откройте базу в браузере, скопируйте ID из адреса (32 символа), затем
     ```bash
     curl -s https://api.notion.com/v1/databases/<ID> -H "Authorization: Bearer $NOTION_TOKEN" -H "Notion-Version: 2025-09-03" | python -c "import sys,json;print([d['id'] for d in json.load(sys.stdin)['data_sources']])"
     ```
   - `output_parent_page_id` — ID страницы для карточек.
   - **Названия полей** обеих баз. Поля базы контактов заданы предположительно — сверьте с реальной базой. `company_match: relation`, если контакт связан с аккаунтом relation-полем; `name` — если связь по названию компании.
   - `allowed_functions` — контакты каких функций берём (остальные попадают в отчёт как пропущенные).
3. Необязательно: добавьте в базу аккаунтов поля `Воронка — статус` (select) и `Воронка — карточка` (url) и впишите их названия в `funnel_status` / `funnel_page` — тогда пайплайн отметит обработанные аккаунты.

## Запуск

Первый раз — маленький батч без записи в Notion:
```bash
python run.py all --batch 5 --dry-run
```
Результат в `runs/<время>/`: по каждому аккаунту `.json` (состояние) и `.md` (поводы, план, проверки, тексты), плюс `SUMMARY.md`.

Затем рабочие батчи:
```bash
python run.py all --batch 20
python run.py sample --run runs/<время> --n 5     # ручная проверка 5 случайных аккаунтов
```
Конкретные аккаунты: `--ids "HitPay,Nomod"` или по Account ID. Этапы можно запускать по отдельности: `select`, `research --run …`, `write --run …`, `review --run …`, `publish --run …`.

Параллельность — `selection.parallel` в конфиге. Лимиты подписки общие для всех вызовов аккаунта: если упираетесь в лимит, уменьшите `parallel` и `batch_size`.

## Правила качества (обязательно)

- **Ручная выборка в каждом батче:** ≥5 случайных аккаунтов. Брак в 2+ из 5 — батч останавливаем, причину превращаем в правило (SPEC §8).
- **Нет повода — нет письма.** Аккаунты `under_researched` не дописываются вручную «из общих слов»: либо доисследовать, либо отложить.
- **Изменение правил** = правка `SPEC.md` + кода/промптов в одном коммите + `python run.py eval` (и `--live` для промптов) + решение Ильи. Правки не дописываются снизу документа — меняется нужный раздел и журнал решений.
- Эталоны в `golden/` — одобренные Ильёй тексты. Их не правят без его решения.

## Структура

```
SPEC.md               правила воронки (источник истины)
config.example.yaml   шаблон настроек без доступов
run.py                оркестратор этапов
pipeline/
  rules.py            выбор оффера, размер/уровни контактов, проверки текстов
  verify.py           проверка цитат по ссылкам
  stages.py           этапы select / research / write / review / publish
  llm.py              вызов claude -p и валидация JSON
  notion.py           клиент Notion API
  render.py           карточка Notion и markdown-отчёт
  models.py           схемы данных
prompts/              промпты исследования, писем, рецензента
golden/               эталонные аккаунты (HitPay, NextPay, Nomod, Dibsy)
evals/run_eval.py     регрессия на эталонах
tests/                тесты без сети
```
