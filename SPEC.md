# Design-Partner Funnel · Спецификация v2.2

Единственный источник правил для аутрича дизайн-партнёрам. Копия страницы в Notion у Ильи.
Код (`pipeline/rules.py`, `prompts/*.md`) реализует этот документ.

**Правило изменений:** любая правка меняет нужный раздел и номер версии, а не дописывается снизу.
Каждая найденная ошибка становится проверкой (§8) или эталоном (§10). Изменение правил =
правка этого файла + кода в одном коммите + прогон `python run.py eval` + решение Ильи.

## 1. Зачем эта воронка

- **Вопрос эксперимента:** какие ICP, размеры компаний и типы оффера приводят к разговору с подтверждённой болью. Результат определяет, куда направить усилия HAIA.
- **Единица работы:** аккаунт с проверенным поводом, а не строка списка.
- **Метрика:** проведённые разговоры и согласия на shadow-прогон / бэктест / проверку встраивания. Процент ответов — промежуточный показатель.
- **Главный сигнал — содержание разговора,** записанное полями (§9). На малых числах процент ответов — шум.

## 2. Отбор аккаунтов и людей (снизу вверх — обязательно)

- Источник: корпоративные базы «Компании» (аккаунты) и «Диалоги» (контакты), связь «Компания». Контрольный сегмент P2P не берём. **Owner назначается после подготовки батча:** компании с заполненным Owner воронка не трогает и сама Owner не ставит. Приоритет выводится из сегмента по документу ICP. Аккаунты без контактов тоже идут в воронку: людей находит этап «люди».
- Контакт с заполненным «Брак: причина» пропускается. Контакт с «Тёплое интро через» не идёт в холодную цепочку: в карточке он попадает в раздел «тёплый путь».

**Кому пишем — лестница ролей (`roles.yaml`).** Источник — «Основные собеседники» документа «HAIA — Financial Buyer Discovery ICP» + правило «снизу вверх». Код читает должность так:

1. Слово из исключений (продажи, маркетинг, HR, разработка, поддержка, юристы…) — не пишем никогда.
2. **Исполнитель** — не руководитель, функция из основных для сегмента (например, для ICP-3: card, program, disputes, operations).
3. **Владелец процесса** — head / director / VP той же функции или COO; в малых компаниях (до 50) — ещё фаундер / CEO.
4. **Ближайший по смыслу** — функция из списка «ближайших» сегмента (product; для ICP-1 и ICP-7 ещё risk, для ICP-5 — compliance) или CEO компании 51+.
5. Должность вне лестницы — не пишем, в отчёт «роль вне лестницы».

| Размер | Получатели | День старта | Минимум для писем |
|---|---|---|---|
| до 50 | Владелец процесса (фаундер / CEO / COO); исполнитель, если есть | день 1 | 1 человек с лестницы с email |
| 51–200 | 1 исполнитель + владелец | исполнитель — день 1, владелец — **день 3** | 1 исполнитель с email |
| 200+ | до 2 исполнителей + владелец | исполнители — день 1, владелец — **день 3** | 1 исполнитель с email |
| неизвестен | как 51–200 | | |

Если владельца процесса с email нет, его место занимает один «ближайший по смыслу». Если никого с лестницы нет — письма не пишем, аккаунт в холде.

**Этап «люди» — несколько заходов до холда:**

Ступени ищутся по очереди, каждая — по должностям из `roles.yaml` для сегмента:

1. Исполнители (в компаниях 51+): поставщик email (Findymail) → веб, заход 1 (команда, спикеры, профили) → веб, заход 2 (вакансии, пресса, кейсы партнёров).
2. Владелец процесса: поставщик → веб.
3. Ближайший по смыслу — только если владельца с email так и нет: поставщик → веб.

- Заходы идут, пока не набрана цель по исполнителям.
- Кандидата из веба код принимает, только если имя есть на странице-источнике или slug LinkedIn совпадает с именем.
- Email для кандидата ищет и проверяет поставщик.
- Найденные люди записываются в базу контактов: с email — статус «Готов», без email — «Нужно обогатить».
- Если после всех заходов минимум не набран: статус `needs_people`, письма не пишутся. В карточке перечислены все заходы. Аккаунт уходит на автоматическую перепроверку через 7 дней.

## 3. Исследование (три захода до холда)

**Заход 1 — корпус собирает код** (окно `collect_days`, 270 дней):

- Google News;
- sitemap сайта (блог, changelog, новости, тарифы, вакансии, документация с датами);
- вакансии Greenhouse / Lever / Ashby;
- YouTube (если есть ключ).

Модель только извлекает поводы из собранного; цитата сверяется с текстом документа.

**Заход 2 — углубление** (если проверенных свежих поводов компании меньше двух). Пять обязательных стратегий модели с WebSearch / WebFetch:

- региональная и отраслевая пресса;
- партнёры и интеграции;
- конференции и подкасты;
- посты руководства;
- реестры и лицензии.

**Заход 3 — рыночный повод** (если у компании нет ни одного): регулятор, платёжные рельсы, дедлайны стандартов на рынке аккаунта.

- **Холд только после всех заходов:** статус `on_hold`, причина перечисляет каждый заход и что он дал. Через 7 дней — автоматическая перепроверка (`run.py recheck`). Ручного «доисследовать» нет.
- **Форма повода (все поля обязательны):** тип (§4) · дата события · URL · дословная цитата до 25 слов · что произошло · что из этого следует для операций · уверенность (EVENT / INTERPRETATION).
- **Проверка цитаты кодом:** код открывает URL и ищет цитату на странице. Не нашлась — повод отклонён. Если сайт закрыт для кода, проверка идёт через WebFetch, пометка `verified_llm`.

**Свежесть — уровни считает код от сегодняшней даты:**

| Уровень | Возраст события | Как использовать |
|---|---|---|
| `hook` | ≤60 дней (MARKET — дедлайн в ближайшие 120 дней) | Можно открывать письмо и поздравлять |
| `state` | 61–270 дней | Только как текущее состояние («NextPay runs…»), **без поздравлений** |
| `context` | 271–365 дней | Только в отчёт, в письмо не идёт |
| `stale` / `invalid` | >365 дней, без даты, будущая дата у не-MARKET | Не повод |

**Нельзя использовать в письме, даже если найдено:** негативные отзывы клиентов, инциденты, увольнения, личная информация о контакте вне рабочей роли.

## 4. Повод → оффер (детерминированно, код)

| Тип повода | Определение | Оффер |
|---|---|---|
| **BUILDING** | Запуск, дорожная карта или найм под функции в нашей области для их клиентов: сверка, статусы платежей, исключения, восстановление, AI в операциях, финансовые инструменты | **PREBUILD** — слой внутри их продукта под их брендом; проверка на их выгрузке |
| **CHANGE** | Изменение тарифов, правил, сроков, процесса, партнёра, лицензии; выход на рынок | **BACKTEST** — проверка изменения на прошлых данных |
| **SCALE** | Цифры роста, новые методы оплаты, рельсы, коридоры, раунд, вакансии в ops / reconciliation / finance | **REPLAY** — shadow-прогон месяца их процесса |
| **MARKET** | Изменение рынка, которое касается их операций: дедлайн регулятора, новая рельса, стандарт | **BACKTEST** — рыночная когорта |
| — | Нет проверенного повода после трёх заходов | Письма нет → `on_hold` |

- **Когорта:** если есть годный повод компании (уровни hook / state), когорта `company`; рыночный повод — только когда своего нет (когорта `market`). Когорта записывается в карточку и в поля эксперимента: это отдельная ячейка анализа.
- **Основной повод (оффер):** среди годных — по приоритету BUILDING > CHANGE > SCALE > MARKET, при равном типе — более свежий.
- **Повод-зацепка (первая фраза):** основной, если он уровня hook. Иначе — самый свежий повод уровня hook. Если такого нет — основной в формулировке текущего состояния.
- **День 3:** если есть годный повод другого типа и другого оффера, не упомянутый в дне 1, — день 3 строится на нём и его оффере. Иначе — гипотеза B по другому процессу с оффером дня 1. Писатель указывает основание; код проверяет.
- **Модель не выбирает оффер.** Она классифицирует повод по определениям (`prompts/_triggers.md`).

## 5. Что можно и нельзя говорить о HAIA

**Можно (подтверждено):** полный след операции в одном кейсе · сигнал, когда кейс отклоняется от ожидаемого пути · подсказка следующего шага · проверка правила на прошлых данных и в shadow-режиме до включения · может работать внутри чужого продукта под их брендом · прогон по выгрузке без интеграции.

**Честная причина поиска партнёров:** база готова; ищем, что строить поверх неё, и хотим найти это на реальных данных платёжных команд, а не угадать. Выгода адресата — надстройка строится вокруг его процесса.

**Нельзя:** клиенты, пилоты, интеграции, цифры эффекта · автономное управление операциями · условия, цены, сроки пилота, лимит мест, лицензии · «у вас этого нет», «ваш инструмент не справляется» · сравнение с конкурентами · «помогите нам собрать» как основа просьбы · название HAIA в теле письма (только в подписи) · внутренний язык базы («value proposition», «Job», «OEM», «WTP», «control plane»).

## 6. Структура сообщений (английский)

**День 1 · Email, до 180 слов без подписи, 5 абзацев:**

1. Повод-зацепка (§4) своими словами. Поздравление — только для уровня hook; для state — текущее состояние; для рыночной когорты — что изменение рынка значит для их клиентов.
2. Допущение — помечено как догадка: «My guess…».
3. База и поиск надстройки: «We have the base in place: …» (2–3 возможности из §5) + «The interesting part is what to build on top, and we want to shape it with a few payments teams on their real data rather than guess.»
4. Оффер одной-двумя фразами: «For {Company}, that could …» (PREBUILD добавляет «under your brand») + «From an export, no integration needed.»
5. Вопрос «A или ваш вариант»: «Worth trying on X, or …?» Созвон не просим.

**Тема:** 2–5 слов, выглядит как внутренняя, связана с поводом.
**День 1–2 · LinkedIn-заметка:** ≤200 знаков; повод + «I emailed you…» + «Would value your view.»
**День 3 · Email в том же треде, до 90 слов:** основание по §4 + оффер одной фразой + вопрос-сравнение с днём 1.
**День 5 · Переадресация, до 45 слов:** «last note» + кто владеет процессом. Без имён коллег.
**Подпись:** день 1 — `Ilia Frolov / CRO & Product Architect, HAIA / haia.finance`; дни 3 и 5 — `Ilia`.
**Крупные аккаунты (200+):** исполнителям — экспертный вопрос о процессе + оффер; руководителю (с дня 3) — с тем, что известно о процессе, без имён исполнителей.

## 7. Каденция

Одна рабочая неделя: День 1 email · День 1–2 LinkedIn · День 3 email в треде · День 5 переадресация. Существенный ответ останавливает цепочку. Даты следующих касаний — только после фактической отправки предыдущего. Выводы — не раньше чем через 3–5 дней после дня 5.

## 8. Проверки

**Код (`pipeline/rules.py::check_package`):** поздравления только при зацепке уровня hook · длины и лимит знаков · запрещённые фразы §5 · HAIA в теле · маркер «My guess» · обязательные фразы §6 · финальный вопрос с «or» · «under your brand» только при PREBUILD · все числа в письме есть в проверенных поводах или фактах базы · основание дня 3 по §4 · приветствие по имени · подписи.

**Рецензент (отдельный вызов без контекста автора). FAIL, если есть хотя бы одно:** старое событие подано как новость · рыночный повод не связан с их бизнесом · утверждение о компании вне проверенных поводов · утверждение о HAIA вне §5 · допущение подано как факт · письмо подошло бы другой компании без изменений · оффер не привязан к их процессу или данным · просьба о созвоне или открытый вопрос без варианта A · оправдывающийся, льстивый или канцелярский тон · перечень модулей.

**Стоп-условия батча (код, `gates` в конфиге; обходятся только `--force`):**

- доля аккаунтов с проверенным поводом < 70% — письма не пишутся;
- доля аккаунтов, где снизу вверх выполнимо, < 70% — письма не пишутся;
- отказов проверок и рецензента > 20% — публикация останавливается.

**Замер перед батчами:** `run.py measure` — 30 аккаунтов поровну по сегментам ICP-1…7, исследование и люди без писем. Таблица `MEASURE.md` по сегментам: доля с поводом, сколько рыночных, доля с людьми, холды. Сегмент ниже порога дорабатывается до писем.

**Выборочная ручная проверка:** в каждом батче человек читает ≥5 случайных аккаунтов (`python run.py sample`). Брак в 2+ из 5 — батч останавливается, причина становится правилом этого раздела.

## 9. Выход и результаты

**Карточка аккаунта в Notion:** когорта · основной повод и зацепка с уровнями свежести · журнал заходов исследования и поиска людей · тёплый путь · контакты (кто с дня 1, кто с дня 3, кому нужен email) · поводы со ссылками и статусом проверки · тип повода / оффера / уверенность · все касания в двух форматах (READ-проза + COPY-блок) · статус «Черновик на ревью».

**Отправка:** только вручную, после одобрения. Пайплайн ничего не отправляет.

**Поля результата:** ответ (нет / негатив / переадресация / интерес / созвон) · на какое касание · какой процесс назвали (A / B / свой) · боль подтверждена · чем закрывают сейчас · владелец процесса · согласие на прогон / бэктест / проверку встраивания.

**Поля эксперимента на строке контакта** (пишет `publish`): тип оффера · тип повода · когорта · уверенность · ссылка на карточку · день старта (1 / 3).

**Анализ:** ICP × размер × когорта × тип оффера × уверенность повода.

## 10. Эталоны и регрессия

- Эталоны: HitPay, NextPay (рыночная когорта), Nomod, Dibsy (`golden/`). Заморожены на дату `as_of`: уровни свежести считаются от неё.
- `python run.py eval` — офлайн: правила выбора оффера и проверки на эталонах. `python run.py eval --live` — писатель и рецензент на эталонных исследованиях.
- Расхождение с эталоном — изменение не принимается без решения Ильи.
- Каждая ручная правка Ильи становится правилом §5–8 или новым эталоном.

## 12. Наполнение базы (этап source)

Верх воронки: добирает аккаунты туда, где база тонкая, и пишет их в базу аккаунтов в том формате, который читает воронка. Дальше — обычный `run.py all`. **Принцип: наверху отсекаем только мусор; доказательства не фильтруют, а записываются пометками. Чистят следующие ступени** (нет повода — холд, нет человека с лестницы — холд).

- **Квоты:** целевое число аккаунтов на сегмент. Код считает текущую базу (без «Research hold»), берёт только дефицит и делит его поровну между регионами.
- **Текущая цель (решение Ильи, 9 Nov 2026):** добрать ICP-3, ICP-5, ICP-6 до 45; регионы — Юго-Восточная Азия, GCC, Латинская Америка и Африка, поровну (ОАЭ и Сингапур уже наполнены, добираем поверх).
- **Поиск — до трёх заходов на ячейку «сегмент × регион»:** реестры лицензий → рейтинги, каталоги, конференции → новости за 12 месяцев.
- **Определения сегментов** — по документу «HAIA — Financial Buyer Discovery ICP» (`prompts/_icp.md`): компания подходит, если ведёт хотя бы одну из финансовых Jobs своего сегмента.
- **Жёстко отсекаем только:**
  - нет домена или сайт не открывается;
  - уже есть в базе (по домену и названию);
  - не ведёт ни одной финансовой Job из ICP (при сомнении — оставляем);
  - страна известна и явно вне региона (неизвестна — оставляем);
  - сегмент компании без дефицита.
- **Пометки уверенности (не фильтр), пишутся в базу:**
  - сегмент: «подтверждён на сайте» / «подтверждён другим источником» / «вывод по описанию» — код сверяет цитату со страницей;
  - размер: «подтверждено ссылкой» / «LinkedIn, кодом не проверено» / «оценка» / «неизвестен»;
  - названа ли компания на странице, где её нашли.
- **Приоритет — по документу ICP:** ICP-1…4 — P1 (ICP-3 — P1 по решению Ильи), ICP-5…7 — P2.
- **Запись в Notion:**
  - поля: компания, домен, сегмент, приоритет, «Ready for enrichment», размер с пометкой, роль владельца процесса, X — факт (что делает + денежный процесс + цитата, если есть), источник, заметка о регионе, пометках и том, где компания найдена;
  - Account ID продолжает нумерацию базы;
  - гипотеза и ценность не заполняются.
- **Отчёт `SOURCE.md`:** дефицит и добавлено по сегментам, ячейки и заходы, распределение пометок, принятые, отклонённые по причинам.
- **Пробный запуск:** `run.py source --batch 5 --dry-run`.
